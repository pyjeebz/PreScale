---

PreScale is designed to give you a meaningful load-test result as fast as possible. You don't write any scripts or configure anything — you install the CLI, point it at a URL, and read the verdict. This guide walks you through the four most useful commands from a cold start.

<Steps>
  <Step title="Install">
    One command, no Python setup needed:

    <CodeGroup>
    ```bash macOS and Linux
    curl -fsSL https://prescale.dev/install | sh
    ```

    ```powershell Windows
    irm https://prescale.dev/install.ps1 | iex
    ```

    ```bash pip
    pip install prescale
    ```
    </CodeGroup>

    Check it worked:

    ```bash
    prescale --version
    ```

    You should see `prescale, version 1.0.0`. If your shell says "command not found", open a new terminal so it picks up the updated `PATH`. [Installation](/installation) has the details.
  </Step>

  <Step title="Run a load test">
    Point PreScale at your local app and ramp traffic up until something breaks:

    ```bash
    prescale run http://localhost:8000
    ```

    PreScale steps virtual users up from 1 to 200 (by default), measuring throughput, latency percentiles, and error rates at each level. When it finds the first level where errors or latency cross the threshold, it marks the break and prints a verdict:

    ```text
    PreScale — load testing http://localhost:8000  (1 route)

     Users   Req/s    p50    p95   vs 2s wall          p99   Errors
        10     520   18ms   31ms   █            ┆       44ms      0%
        50     610   46ms  120ms   █            ┆      210ms      0%
        90     590   80ms  240ms   ██           ┆      900ms      0%
       150     410  180ms   2.1s   ░░░░░░░░▒▒▒██┆        3.4s      7%

    Scale readiness: ⚠️  Survives ~90 (75–110) concurrent users
    Ramp       ░░░░░░░░░▒▒▒██         ~90 of 150 users tested
    Traffic    ≈ 590 req/s, roughly 5,900 real visitors
    ```

    How to read it:

    - **The verdict** comes with a confidence band (`75–110`), so you can see how much to trust the number.
    - **Each bar** runs from sparse `░` to a solid `█` at that stage's p95 latency, toward the latency wall `┆` (2s by default). A bar reaching the wall is where users start to feel it.
    - **Traffic** turns the user count into load: a virtual user sends requests back to back, while a real visitor pauses between clicks, so ~90 users here is roughly 5,900 people browsing (assuming one request per visitor every 10 seconds).

    Every run is saved to `./.prescale/runs/` for later inspection.
  </Step>

  <Step title="Investigate why">
    `prescale run` tells you *what* breaks. `prescale investigate` tells you *why* and *how to fix it*. It finds the culprit route, probes it under load vs at baseline, classifies the bottleneck, and prescribes a concrete fix — all locally, with no LLM involved:

    ```bash
    prescale investigate http://localhost:8000
    ```

    Example output:

    ```text
    🔬 Diagnosis
    Likely cause: 5xx under load while static assets held — the app/backend is the wall.
    Bottleneck  connection_pool (high confidence)  ·  culprit /api/search
    Evidence
      • culprit p95 28ms at 1 user vs 2100ms at 150 users
      • static /assets/app.js held at 150 users
      • errors under load: 5xx (180)
    Try this
      → Increase the DB/upstream connection-pool size.
      → Add a pooler (e.g. pgbouncer) and check the pool checkout timeout.
    ```

    You can also re-investigate the most recent saved run without re-running the ramp:

    ```bash
    prescale investigate
    ```
  </Step>

  <Step title="Audit HTTP hygiene">
    Before you worry about concurrency, make sure your app isn't leaving performance on the table at the HTTP layer. `prescale audit` runs a fast, load-free check of compression, caching, CDN presence, and HTTP version — no traffic ramp required:

    ```bash
    prescale audit https://myapp.com
    ```

    Example output:

    ```text
    ✓ Compression           Responses are compressed (br).
    ⚠ HTTP version          Served over HTTP/1.1.
    ⚠ Static asset caching  2 of 6 sampled assets have no caching headers.
    ✓ CDN / edge cache      Detected (Cloudflare).
    ```

    This command is cheap enough to run on every commit in CI.
  </Step>

  <Step title="Keep it on every deploy (optional)">
    Everything above runs on your machine and needs no account. To keep a history of every run and check each pull request, connect the CLI to your free dashboard:

    ```bash
    prescale login
    prescale investigate https://staging.myapp.com --i-own-this --upload
    ```

    Then add the [GitHub Action](/guides/github-action): every preview deploy gets one PR comment with the capacity change against `main`, what breaks first, and the fix. [What gets uploaded](/reference/data-boundary) lists exactly what leaves your machine.
  </Step>
</Steps>

<Tip>
  When testing a staging URL you own, add `--i-own-this` to skip the confirmation prompt:

  ```bash
  prescale run https://staging.myapp.com --i-own-this
  ```

  This is especially useful in CI pipelines, where there's no interactive terminal to respond to a prompt.
</Tip>

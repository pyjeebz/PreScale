Most capacity problems live in your app's code and database: a slow query, a small
connection pool, a blocking call. You don't need your host to find them, and many hosts
don't allow load tests anyway (Vercel only permits them on Enterprise plans). So PreScale can
run your app itself:

```bash
prescale investigate http://localhost:3000 --app "npm run build && npm start"
```

PreScale:

1. Starts the command in your project, the same way you would.
2. Waits until the URL answers. Production builds take a while, so it waits up to 10 minutes
   (`--app-timeout`).
3. Runs the test against `localhost`.
4. Stops the app **and everything it started**, even after an error or Ctrl-C.

No host is involved, so no host's load-testing rules apply and no CDN's cache or firewall
shapes the result.

## On your machine

`--app` works on [`run`](/commands/run), [`investigate`](/commands/investigate) and `ci`.

```bash
# A Next.js app
prescale investigate http://localhost:3000 --app "npm run build && npm start" --upload

# A Python API on another port, with the routes that matter
prescale run http://localhost:8000 --app "gunicorn app:app -b 127.0.0.1:8000" \
  --path /api/search --path /api/checkout
```

The URL must be local. If something is already answering there, PreScale stops instead of
testing it, so you always test the build it started. If the app crashes or never comes up,
you get its exit code and the end of its log.

## A throwaway copy of your database

With `--db neon`, the app doesn't use your staging database at all. PreScale copies a Neon
branch you name, points the app at the copy, and deletes the copy when the test ends.

```bash
export NEON_API_KEY=...        # a Neon API key
export NEON_PROJECT_ID=...     # the project to copy from
prescale run http://localhost:3000 --app "npm run build && npm start" \
  --db neon --db-parent staging
```

- **Safe writes.** Journeys that write (sign-ups, carts, orders) change the copy, never
  `staging`.
- **Real data, real query plans.** Neon branches are copy-on-write, so the copy has all of
  the parent's data within seconds, whatever its size.
- **Its own compute.** The load runs on the copy's compute, not the parent's. That compute may
  be sized differently from production's, and results say so.
- **Always cleaned up.** The copy is deleted however the run ends. If Neon refuses, PreScale
  names the branch (`prescale-...`) so you can delete it.
- **You choose the parent.** `--db-parent` is required: the default branch is often
  production, so PreScale never picks it for you.
- **The connection string stays secret.** It goes into the app's environment only (as
  `DATABASE_URL`, or the variable you name with `--db-env`), never into the terminal, the
  saved run or an upload.

- **Every database variable points at the copy.** Besides `DATABASE_URL` (or the variables you
  name with `--db-env`, repeatable), PreScale always sets `DIRECT_URL`, `POSTGRES_URL`,
  `POSTGRES_PRISMA_URL`, `POSTGRES_URL_NON_POOLING`, `DATABASE_URL_UNPOOLED` and the `PG*`
  variables to the copy, even if they aren't set. Apps often load these from a `.env` file,
  and dotenv never overrides a variable that's already set, so the copy wins over the file.
  Any other variable holding a Postgres URL gets a warning: add it with `--db-env`.
- **Secrets stay out of logs.** If the app fails to start, the end of its log is shown with the
  copy's URL and password replaced by `***`, and the log file is deleted.
- **Cancelled CI jobs clean up too.** The first Ctrl-C or SIGTERM (a cancelled GitHub Actions
  job) stops the app quickly and deletes the copy; further signals are ignored so they can't
  interrupt the delete.

Options: `--db-name` picks the database when the branch has more than one, and `--db-pooled`
gives the app Neon's pooled URL.

### Leftover copies

A run that's killed outright (a machine that dies, `kill -9`) can't delete its copy, and Neon
plans limit how many branches a project has. `prescale db cleanup` lists PreScale's own copies
(named `prescale-<date>-<time>-<id>`, never a default or protected branch) older than six hours (`--older-than HOURS`) and deletes them after you confirm
(`--yes` to skip). It never touches a branch PreScale didn't make.

## In CI, on every pull request

In CI, replica mode needs no deploy at all: the [GitHub Action](/guides/github-action)
builds the pull request in the job, tests it there and comments the capacity change on the
pull request. Pushes to `main` record the baseline.

```yaml
- uses: pyjeebz/prescale/action@v1
  with:
    token: ${{ secrets.PRESCALE_TOKEN }}
    target: myapp.com
    app: npm run build && npm start
  env:
    DATABASE_URL: ${{ secrets.STAGING_DATABASE_URL }}
```

## Good to know

<Warning>
Your app runs with your environment. Point `DATABASE_URL` and API keys at a dev or staging
database, never production: the load reaches whatever your app talks to.
</Warning>

- **What it measures:** your app's own build on that machine. Serverless behaviour such as
  cold starts isn't included, and the absolute numbers depend on the machine. The change
  between two runs on the same kind of machine (`main` against a pull request) is the signal.
- **Results are marked:** `config.replica` is `true` in the [result](/reference/result-schema),
  and the report says it was measured on a local replica.
- **The command stays private:** it's never saved or uploaded, since it may carry secrets.
- **Coming next:** throwaway database branches (Neon first, then Supabase), so the replica
  gets realistic data without touching your real database.
